Digo

La distribuidora vende en el mostrador de cada sucursal y también en línea, sobre el mismo inventario. Sin un sistema común, la misma blusa se puede vender dos veces, y cuando una clienta devuelve una prenda nadie sabe si volvió a la venta o si se le devolvió el dinero.

Nuestra solución tiene tres piezas: la tienda para las clientas, el panel para los empleados y una API que concentra todas las reglas.

Cada persona ve solo lo que le toca: el cajero y el bodeguero, su sucursal; el administrador, su sucursal completa; y el gerente distrital, todas. Ahora Oswaldo se los muestra en vivo.

Diapositivas 6 a 9 · Arquitectura, reglas, dinero y seguridad

Carlos
Hago

  • 7: estados (≈50 s).
  • 8: dinero e inventario (≈60 s).

Digo

Son dos aplicaciones React, la tienda y el panel, que hablan con una API en Node.js con Express y Sequelize sobre PostgreSQL en la nube. Los pagos van por Stripe y las fotos por Cloudinary. Todo está publicado en Render.

Cada pedido y cada devolución siguen estados definidos; el sistema no deja saltarse pasos ni repetir una devolución.

Lo más delicado es el dinero y el inventario: cada venta bloquea la prenda en la base hasta confirmar, así que dos cajeros no pueden vender la última unidad. Los reembolsos llevan una clave para que reintentarlos nunca devuelva dos veces.

En seguridad, las contraseñas se guardan cifradas, las sesiones se cierran al cambiar la contraseña, y cada consulta se filtra por la sucursal del empleado en el servidor, no en la pantalla.

Preguntas

Respuestas cortas

Respondan primero con la frase corta. Den el detalle solo si insisten.

¿Qué pasa si dos cajeros venden la última prenda a la vez?

Solo una venta se completa. La otra recibe «stock insuficiente» y no se descuenta nada.

Si insisten: cada venta corre dentro de una transacción que bloquea la fila de inventario de esa prenda (SELECT … FOR UPDATE). La segunda venta espera a que la primera termine y entonces ve que ya no hay stock. Todas las ventas bloquean las prendas en el mismo orden, así que no se traban entre sí. Lo comprobamos con pruebas que lanzan ventas simultáneas.

¿Cómo evitan que una sucursal vea los datos de otra?

El filtro está en el servidor, no en la pantalla: cada consulta se limita a la sucursal del empleado. Si alguien pide un pedido de otra sucursal, el sistema responde que no existe.

Si insisten: en cada petición el servidor lee el token, busca al empleado en la base y toma su sucursal de ahí, no de lo que envía el navegador. Fuera de su alcance responde 404, así ni siquiera confirma que el registro existe. Solo el gerente distrital ve todas. Hay 117 verificaciones automáticas de este alcance.

¿Qué pasa si falla el pago?

El pedido queda pendiente con las prendas reservadas, la clienta puede reintentar con otra tarjeta, y si no paga en 24 horas se cancela solo y el stock vuelve a la venta.

Si insisten: si Stripe sí cobró pero la confirmación se perdió, un webhook firmado o la revisión periódica lo registra y el pedido pasa a pagado. Si Stripe cobra un pedido que ya se había cancelado, el sistema devuelve el dinero a la tarjeta automáticamente. Nunca se cobra dos veces el mismo saldo.

¿Guardan los datos de las tarjetas?

No. La tarjeta se escribe en un campo de Stripe y va directo a Stripe; nuestro servidor solo recibe el resultado del pago.

¿Qué pasa si la clienta quiere devolver después de 24 horas, o devolver dos veces?

El sistema no lo permite: solo hay una solicitud por pedido, dentro de las 24 horas desde la entrega. El plazo es configurable.

¿Cómo se calcula el reembolso si usó un cupón?

Se le devuelve lo que pagó por esa prenda: su precio menos la parte proporcional del descuento. El envío no se devuelve.

¿Qué pasa si se cae el servidor o se borra la base?

La base está en la nube (Neon) y tenemos respaldos con un comando; la restauración guarda primero una copia del estado actual por si algo sale mal. El panel muestra el estado del sistema y los errores registrados.

¿Cómo cambian la base de datos sin perder información?

Con migraciones: cada cambio es un archivo numerado que se aplica una sola vez al arrancar y solo agrega, nunca borra columnas.

¿Cómo probaron que funciona?

Con pruebas automáticas que levantan una base de datos desechable y usan la API y las pantallas reales: más de mil doscientas verificaciones con un comando, npm test.

¿Por qué tarda la primera vez que se abre?

Por el plan gratuito de Render: el servidor se duerme tras 15 minutos sin uso y tarda unos 50 segundos en despertar. En un plan pagado no pasa.

¿Qué mejorarían?

Un servidor de correo propio para los avisos a las clientas, un plan de hosting sin pausas y reportes por temporada.
